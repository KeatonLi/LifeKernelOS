# LifeKernelOS 规格驱动开发（SDD）约定

> SDD：Spec-Driven Development，规格驱动开发。
> 目标：用小而明确的规格约束每次变更，先验证要做什么，再决定怎么实现。

## 1. 为什么采用 SDD

LifeKernelOS 的风险不是功能做不出来，而是很容易在“人生管理系统”这个大方向上不断扩张。SDD 用每个小场景的可验收规格控制范围，保证：

- 每次只解决一个具体用户问题。
- 产品行为先于技术实现被讨论和确认。
- 需求、实现、测试和验收可以互相追溯。
- 发现问题时优先修改规格，而不是悄悄让代码偏离产品意图。

## 2. 文档层级

```text
docs/PRD.md
  └── docs/specs/NNNN-*.md
        └── 代码、测试、验收记录
```

- `PRD.md`：只描述当前 MVP 的目标、边界和整体行为。
- `architecture.md`：描述当前 MVP 的技术边界、模块关系和运行约束。
- `docs/specs/`：每个可独立交付的小场景一份规格，是开发时最直接的依据。
- `docs/decisions/`：只有当架构或产品选择会影响多个规格时，才记录决策。
- 未来路线图另建文档，不把未验证的计划混入当前 MVP。

## 3. 一个规格的生命周期

```text
Proposed → Accepted → Implementing → Implemented → Verified
                                      ↘ Superseded
```

- `Proposed`：已提出，尚未确认范围。
- `Accepted`：范围、行为和验收标准已确认，可以开始开发。
- `Implementing`：正在实现。
- `Implemented`：代码和自动化测试已完成，等待验收。
- `Verified`：按规格完成验收，可以合并或发布。
- `Superseded`：被新规格替代，保留历史记录但不再作为当前依据。

没有进入 `Accepted` 的规格，不开始对应实现；没有进入 `Verified` 的规格，不宣称该功能完成。

## 4. 每次开发的流程

### 第一步：提出一个小场景

用用户在真实生活中的一句话描述问题，例如：

> 我只有 30 分钟且精力较低时，希望知道今天能推进的最小行动是什么。

同时写清楚本次不解决什么，避免从一个场景扩展成一整套系统。

### 第二步：写规格

规格至少包含：

- 用户目标和使用前提。
- In scope / Out of scope。
- 用户可见行为。
- 数据字段和状态变化。
- Given / When / Then 验收场景。
- 异常、空状态和可恢复行为。
- 测试清单和待决问题。

### 第三步：规格审查

开发前先质疑四件事：

1. 这是当前用户最需要的场景吗？
2. 能否删掉一半字段和交互仍然验证假设？
3. 每条验收标准是否可以被明确判断为通过或失败？
4. 是否偷偷引入了未来功能、复杂架构或不可逆的数据承诺？

### 第四步：按规格实现

先实现能贯穿用户流程的最小切片，再补充必要测试。不要为了“以后可能用到”提前实现扩展点。

### 第五步：验证并记录偏差

完成后逐条执行验收场景，记录通过、失败和与规格不一致的地方。若实际产品行为更合理但偏离了规格，先更新规格，再更新测试和代码。

## 5. 规格与代码的追溯方式

- 每份规格使用稳定编号，如 `SPEC-0001`。
- 代码中的关键测试名称包含规格编号。
- 提交信息包含规格编号和中文变更说明，例如：`实现 SPEC-0001 当前主线与行动`。
- 一个提交尽量只对应一个规格；若必须拆分，提交之间保持可独立理解。
- PR 或交付说明中列出：实现了哪些场景、验证了哪些场景、哪些内容明确未做。

## 6. 技术架构如何参与 SDD

- 产品行为写在 PRD，技术边界写在 `architecture.md`，具体交付行为写在 `docs/specs/`。
- 新增跨规格的技术选择，先写 ADR，再修改受影响的规格。
- 规格中只声明必要的接口和不变量，不提前固定页面组件、数据库库表细节或未来扩展点。
- 实现阶段不得让 UI 直接读写数据库；所有写操作都经过应用用例和领域规则。
- 如果实现过程中发现架构无法满足规格，先暂停编码，更新规格或 ADR，再继续实现。

## 7. 当前开发顺序

第一轮只按以下顺序推进：

1. `SPEC-0001`：当前主线与行动的创建、查看和完成。
2. `SPEC-0002`：根据精力和可用时间选择下一步。
3. `SPEC-0003`：延后、拆小、放弃和卡住。
4. `SPEC-0004`：日终收束。
5. `SPEC-0005`：快速捕捉，验证确有需要后再做。
6. `SPEC-0006`：周复盘，等日常闭环有真实使用数据后再做。

前四个规格完成并验证前，不引入价值观体系、AI、同步、日历或社交能力。

## 8. 一次完整的 SDD 实践

以 `SPEC-0001` 为例，一次交付应产生以下结果：

1. 在规格中写清楚当前主线、行动字段、状态转换和验收场景。
2. 在架构中确认页面只能调用 `CreateFocus`、`CreateAction`、`CompleteAction` 等用例。
3. 先为领域校验和状态转换编写测试，再实现 IndexedDB 适配器和页面。
4. 用端到端测试执行“首次进入 → 创建主线 → 创建行动 → 完成行动”。
5. 逐条勾选规格验收清单，记录未做项和偏差。
6. 只有验证完成后，才把规格状态改为 `Verified`，并提交中文 commit。

## 9. Definition of Done

一个规格只有同时满足以下条件才算完成：

- 规格状态为 `Verified`。
- 范围没有超出 `In scope`。
- 核心行为有自动化测试或可重复的验收步骤。
- 空状态、错误状态和数据恢复路径已经验证。
- 用户可以完成规格描述的完整流程。
- PRD、规格状态和提交记录保持一致。
