# LifeKernelOS 产品需求文档（MVP）

> 版本：0.2
> 状态：Proposed
> 更新时间：2026-09-04

## 1. 这次只解决什么问题

LifeKernelOS 的第一个版本只解决一个问题：

> 当用户感到混乱、时间有限或精力不足时，帮助用户找到一个现在真正能做的下一步行动，并在行动没有完成时轻松调整。

这不是完整的“人生操作系统”，而是未来产品闭环中的第一个可验证切片。

```text
当前主线 → 下一步行动 → 根据状态选择 → 完成或调整 → 日终收束
```

## 2. 目标用户与核心场景

### 2.1 首个目标用户

暂时只服务已经有明确工作或个人项目、但经常被多件事情打断的个人用户，例如独立开发者、知识工作者和创作者。

### 2.2 核心场景

用户准备开始工作，但面对一堆待办，不知道现在先做什么；用户告诉系统当前精力和可用时间，系统帮助他选择一个合适的下一步。行动没有完成时，用户可以拆小、延后或放弃，而不是积累一条新的失败记录。

## 3. 产品假设

如果用户能用很低的记录成本，根据当前状态快速得到一个合适的下一步，并能无压力地处理未完成事项，那么他会比使用普通待办清单更愿意持续使用这个工具。

MVP 只验证这一个假设，不同时验证价值观管理、AI 复盘、跨工具整合等更大的假设。

## 4. MVP 目标

- 新用户在 2 分钟内创建一条当前主线和至少一条行动，首屏可以继续补充行动。
- 用户在 30 秒内完成一次“我现在该做什么”的选择。
- 用户可以用一次操作完成、延后、拆小或放弃行动。
- 用户可以在一天结束时用不超过 1 分钟记录当天的推进和阻力。
- 用户登录后，在支持的不同设备上仍能看到同一份主线、行动和日记录。
- 首轮试用中，用户能够连续使用 7 天，并明确表示产品帮助自己更快开始行动。

## 5. MVP 不做什么

以下内容不进入当前版本，未来需求另建文档维护：

- 完整价值观、角色、边界和身份系统。
- 多层方向、目标、项目树和复杂依赖关系。
- AI 生成的复盘、建议或心理状态判断。
- 日历、第三方待办、笔记工具同步。
- 社交、打卡、排行榜和公开分享。
- 公开注册、复杂账户体系、团队协作和权限管理。
- 离线编辑、冲突解决和复杂的多端同步队列。
- 提醒中心、复杂搜索、统计报表和个性化主题。
- 周复盘。先验证日常行动闭环，再决定是否需要引入。

## 6. 具体落地场景

### 场景一：首次创建当前主线（P0）

用户第一次进入产品，填写一句话描述当前最想推进的事情，并填写完成标准。然后创建至少一条下一步行动，产品可以建议用户继续补充到 3 条。

最小字段：

- 当前主线：名称、完成标准。
- 行动：名称、预计耗时、精力要求、状态。

验收标准：用户不填写价值观、角色等额外信息，也可以进入今日页面并开始第一条行动。

### 场景二：根据当前状态选择行动（P0）

用户打开今日页面，选择当前精力和可用时间，看到符合条件的行动，主动选择一条作为当前行动。

状态选项保持简单：

- 精力：低 / 中 / 高。
- 时间：15 分钟 / 30 分钟 / 60 分钟。

验收标准：系统展示行动时说明匹配依据；用户始终可以查看全部行动并手动选择，不被自动排序限制。

### 场景三：处理未完成行动（P0）

用户完成行动后标记完成；没有完成时选择一种处理方式：

- 延后：选择下一次处理时间。
- 拆小：修改为更小的下一步。
- 放弃：从当前主线中移除，并可选填原因。
- 卡住：保留行动并记录一句阻力。

验收标准：任何未完成行动都有明确去处，不会只停留在“逾期”状态。

### 场景四：日终收束（P0）

用户在一天结束时用三个问题完成收束：

1. 今天推进了什么？
2. 什么让我卡住或消耗？
3. 明天的最小一步是什么？

三个问题都允许跳过，记录可以只有一句话。

验收标准：用户能看到当天选择的行动、处理结果和收束记录；不要求形成完整日记。

### 场景五：快速捕捉（P1）

用户临时想到任务或想法时，只填写一句话，先放入收件箱，稍后再转成行动或删除。

这是重要的配套能力，但不阻塞第一条主线和行动闭环的验证。

### 场景六：周复盘（P1）

根据一周的完成行动和日终记录，使用固定模板帮助用户决定下周保留、停止和开始什么。延期、拆小、放弃和卡住的历史统计需要后续事件记录能力，不在这一版复盘中承诺。

第一版不引入 AI，不做复杂趋势图，不给出未经用户确认的结论。

## 7. 信息架构

首版只保留三个主要页面：

1. 登录：完成最小身份验证。
2. 当前主线：设置当前主线和行动。
3. 今日：记录状态、选择下一步、处理行动。
4. 日终收束：查看当天行动并完成简短记录。

快速捕捉可以作为全局入口；设置页只提供数据导出和清空数据。

## 8. 最小数据模型

### Focus：当前主线

- `id`
- `title`
- `done_definition`
- `status`：active / completed / archived
- `created_at`、`updated_at`

首版同时只允许一条 active 主线。

### Action：行动

- `id`
- `focus_id`
- `title`
- `estimated_minutes`
- `energy_required`：low / medium / high
- `status`：available / completed
- `created_at`、`updated_at`

当前 MVP 只实现 `available → completed`。`inbox`、`deferred`、`dropped`、`blocked` 和计划时间由后续规格分别引入；“今日选中的行动”不属于 Action 状态。

### DailyState：每日状态

- `date`
- `energy`：low / medium / high
- `available_minutes`
- `selected_action_id`

### DailyClose：日终收束

- `date`
- `progress_note`
- `blocker_note`
- `next_step_note`
- `created_at`、`updated_at`

### User / Session：身份与会话

MVP 只提供受控的个人账号，不开放公开注册、组织和角色权限。业务数据都属于当前登录用户，由服务端按用户隔离。

- `User`：`id`、`email`、密码摘要、创建时间。
- `Session`：`id`、`user_id`、过期时间、创建时间。

## 9. 核心规则

- 今日选中的当前行动最多一条，由 `DailyState.selected_action_id` 表示；用户可以主动更换。
- Action 不使用 `selected` 状态，避免把每日上下文和行动生命周期混为一谈。
- 只有预计耗时不超过可用时间、且精力要求不高于当前精力的行动，才作为默认候选。
- 没有匹配候选时，系统只提示“查看全部”或“新建更小行动”，不强行推荐。
- 完成、延后、拆小、放弃和卡住都属于有效结果。
- 系统不得用连续打卡、失败次数或逾期数量惩罚用户。
- 所有智能排序都必须允许用户手动覆盖，并能说明依据。

## 10. MVP 验收标准

- 新用户能在 2 分钟内创建主线、行动并进入今日页面。
- 用户能在今日页面记录状态，并选择一条匹配的行动。
- 用户能完成、延后、拆小、放弃或标记卡住当前行动。
- 日终收束可以在 1 分钟内完成，也可以跳过。
- 刷新页面或在另一台已登录设备打开后，主线、行动、状态和收束记录仍然存在。
- 用户可以导出当前账号的 JSON，并可以清空当前账号的数据。
- 桌面端和移动端都能完成核心流程；不在首版追求分别设计两套体验。

## 11. 首轮验证指标

这些数字是首轮试用假设，不是长期 KPI：

- 至少 5 名真实用户完成 7 天试用。
- 至少 3 名用户在 7 天内使用 4 天以上。
- 用户从打开今日页到选择行动的中位耗时不超过 30 秒。
- 至少一半用户认为“选择下一步”比原来的待办方式更容易。
- 访谈中没有出现“记录本身比行动更累”这一主要负面反馈。

## 12. 服务端边界

- React 只通过 API 访问业务数据，不直接连接 PostgreSQL。
- 服务端是数据事实源；浏览器端不承担跨设备同步和最终持久化责任。
- API 通过 HttpOnly 会话 Cookie 识别当前用户，所有业务查询和写入都必须带用户边界。
- MVP 部署为后端服务加 PostgreSQL；前端构建产物可以由同一个后端服务提供。
- 服务端不记录用户正文到第三方分析平台，也不引入 AI 调用。
