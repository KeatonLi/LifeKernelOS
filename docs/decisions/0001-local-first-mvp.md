# ADR-0001：MVP 采用本地优先架构

> 状态：Superseded
> 日期：2026-09-04
> 影响范围：MVP 全部规格

> 本决策已被 [ADR-0003 服务端持久化 MVP](0003-server-backed-mvp.md) 替代。保留本文用于记录早期取舍。

## 背景

当前 PRD 的目标是验证用户是否愿意根据当前精力和可用时间选择下一步行动。这个假设不依赖账号、多人协作、跨设备同步或 AI。若首版先搭建后端，会把验证重点从“行动闭环”带到登录、接口、部署和数据同步。

同时，产品处理的是用户的个人计划和生活记录，首版需要一个清晰、容易解释的隐私边界。

## 决策

MVP 采用响应式 Web 单体和本地优先存储：

- 前端使用 React + TypeScript + Vite。
- 核心数据保存在浏览器 IndexedDB。
- 不建立账号系统和后端 API。
- 用仓储接口隔离领域逻辑与具体存储实现。
- 提供 JSON 导出和清空本地数据。

## 为什么不是其他方案

### 直接使用后端数据库

会提前引入账号、鉴权、部署、数据迁移和隐私政策等问题；这些不是当前产品假设的一部分。

### 只使用 localStorage

虽然更简单，但缺少事务、结构化查询和后续数据迁移能力；行动、每日状态和日终记录已经适合 IndexedDB。

### 先做跨端原生应用

会同时引入原生开发、打包和分发成本，无法更快验证核心流程。响应式 Web 足够覆盖首轮试用。

## 代价与接受条件

- 用户换浏览器或设备时不会自动同步；这是 MVP 明确接受的限制。
- 用户清理浏览器数据可能丢失记录，因此必须提供 JSON 导出和清空数据入口。
- 浏览器存储能力和隐私策略存在差异，应用必须在初始化失败时明确告知用户。
- 未来如果需要同步，必须新建 ADR，明确账号、冲突、加密和迁移策略。

## 重新评估触发条件

出现以下任一情况时重新评估本决策：

- 真实用户明确要求在多个设备间同步。
- 本地数据规模影响性能或可靠性。
- 需要多人共享或协作。
- 需要在服务端执行用户主动授权的 AI 能力。
