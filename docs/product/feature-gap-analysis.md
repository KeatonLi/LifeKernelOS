## 回顾必须先明确的数据边界

当前数据库保存任务的当前状态与处理时间，有主线状态事件和 AI 拆解回执，但没有覆盖每次任务完成、撤销、卡住、恢复、移除的完整事件流。撤销完成后，不能从当前状态还原“这一周曾经完成过又撤销”的完整历史。

轻量第一版可以展示仍存在的完成事实，加用户主动填写的推进与下一步；若要统计每一次历史处理，应先定义任务事件、时间/日期、撤销语义、备份版本及迁移规格，再实现统计。不能先画趋势图再用当前状态猜历史。

## 已有实现但待验收

- 真实用户 Key / 模型权限、建议质量、离线与超时体验。
- macOS / Windows / Linux 系统密钥服务及权限提示；CI 的会话 Key 不替代加密持久化实机验收。
- 原生文件对话框、全局快捷键被占用时的体验、最小窗口实际操作及安装器安装。
- 正式代码签名和 macOS 公证尚未配置，属于发布能力缺口；需要对应证书、身份及发布配置。
- PRD 中的 5 名用户、7 天试用及行动耗时目标没有新的验收记录，不能宣称已达成。

## 明确不属于当前版本的能力

提醒、重复任务、外部日历同步、云同步、移动端、团队协作和 OKR 层级在当前 PRD 明确不纳入本版，不能作为实现漏项。原生 Anthropic 协议、多个 AI 连接与全库上传也不在当前 BYOK 拆解范围。

## 建议推进顺序

1. 先补知识标题/说明编辑与原生品牌图标，完成真实桌面和 Key 验收：直接改善现有使用流程。
2. 试用中确认“知道目标但不会开始”的实际需求后，优先交付 AI“帮助开始”的一个小切片，再评估“处理卡住”；复用既有 BYOK 与显式采纳边界。
3. 根据回看需求单独接受事实概览和轻量回顾，先定清当前事实与历史事件的区别。
4. 自动升级与签名、公证按发布阶段推进；同步、提醒和循环任务按反复出现的真实需求排期。

本顺序是基于仓库现状的建议，不是已经确认的路线图或交付日期。新场景进入实现前更新 PRD / Spec；本轮只落实下面的小优化。

## 本轮已落实的小优化

- 导出采用独立 UUID 临时文件、排他创建、完整写入后原子替换，失败只清理本次暂存文件；多窗口同路径写入串行，Windows 短暂文件锁采用有限重试，失败后可重新导出。
- 导出默认文件名使用本地日期，与任务日期语义一致。
- Actions 上传安装包关闭重复压缩；下载安装包的目录结构与 SHA-256 发布校验保持一致，依据 [upload-artifact 官方说明](https://github.com/actions/upload-artifact#altering-compressions-level-speed-v-size)。
- 跨平台界面测试明确等待初次渲染完成，以简短错误校验 DOM 元素身份；全量测试最多并行两个文件进程，减少托管 runner 的资源争用，不放宽任务、焦点和草稿断言。

验证命令包括全量业务/HTTP/DOM/恢复回归、类型检查、生产构建、Windows x64 真实 Electron 导出并发/取消与任务/AI/导入/重启闭环和 actionlint。最终结果见 main 的 Actions 运行；原生人工验收仍按上节记录。
